# 1.0.1 登录修复验证

日期：2026-11-14。范围是原 Mac 协调桥登录恢复、监控 Web 的真实登录核验及本项目发布版本更新；运行依赖保持原版本。

## 已定位故障

用户看到的是浏览器拒绝连接本机回调端口，不是 OAuth `access_denied` 页面。原桥受控诊断中，浏览器在登录开始后 19.08 秒打开，回调在 20.88 秒被取消，20.89 秒返回 `MCPError -32001`，错误位置为自动协议回退后的 `initialize`。整个尝试结束后恢复了原 collector。

在固定 FastMCP 4.0.11／MCP 2.3.0 中，正常 OAuth 浏览器等待会暂停当前请求计时，因此单独看到 10 秒配置不足以证明故障。隔离复现也确认旧实现能等待超过 10 秒。慢认证准备导致 `server/discover` 先超时并开始另一个 `initialize` 时，仍在进行的授权暂停的是前一个请求时钟，后一个请求仍会超时并终止连接。本机登录进程结束后端口关闭，浏览器再跳回就遭到拒连。

## 修复与范围

固定代码提交 `6b3571fcb65677d656eb9df5d73c2e17637de3b9`：交互登录直接使用服务已有的 legacy 握手，连接与请求预算 330 秒，SDK 浏览器回调仍限 300 秒。授权后 `whoami` 显式限时 10 秒；正常 collector 仍为 auto 模式、10 秒请求及原有非交互认证限制。没有修改 OAuth App、凭据来源、账号权限、数据库或依赖版本。

FastAPI 与 Web 项目版本由 1.0.0 更新至 1.0.1。仓库此前无应用 Release/tag，仍按固定提交部署。

## 真实登录

Mac 原安装目录的 16 个文件已更新到上述固定提交。公子完成新页面授权，实际浏览器等待 79.02 秒后收到回调，`whoami` 成功，认证为 `READY`。原 collector 已恢复并完成 `OK / ROUND_COMPLETE`，协调端口 `READY`。原 8 个任务、0 个待回报及 0 个 UNKNOWN 保持。旧 network 错误行仍保留原时间，新的 authentication／collector 状态是本轮恢复证据。

服务端日志同时表明旧桥 refresh token 已无法找到，返回 `invalid_grant`；该日志不能区分已轮换、过期或撤销。重新登录沿原桥身份和专用缓存办理，没有借用其他客户端令牌。

监控 Web 另从公网专用入口发起登录。公子明确回报已进入监控页面并看到凡人项目。它的回调为公网 `/mailbox/auth/callback`，不是本机回环；本轮未发现需要修改 Web 认证逻辑的证据。模拟测试、Mac `whoami` 与这次实际 Web 用户回报分别记证。

## VPS 发布

固定源码和五份 Web 构建摘要已上传，VPS 独立回归 203 项全部通过，无跳过。第一次启动观察 20 秒内未监听，发布脚本恢复并核对旧版 1.0.0 继续服务；日志没有该次新进程的启动错误。保留失败回执并重新核对同一固定发布后，使用有界的 60 秒就绪观察。

第二次激活已通过：118 个发布文件摘要匹配，实际进程工作目录为上述固定提交，OpenAPI 版本为 1.0.1，Web 首页摘要为 `76e1772ba85be4863efd2ab920cef5b153b15550f59470a5780c8cc3a2d4de67`。其间一次 PG 临时连接不可用以 75 退出，既有 systemd 策略重启 1 次后就绪；没有变更重试策略、数据库配置或依赖。这个短样本不证明长期网络稳定性。

发布后原生 MCP `whoami` 和 `mailbox_usage` 实际成功，原信箱计数仍为 8／8／24，观测为 20／3，统一 PostgreSQL 模式保持。真实 Web 登录后查到 1 个活动浏览器会话。

后续公子指示将 Web 改到 Mac 本机并关闭 VPS Web，实际结果见[本机监控记录](local-monitor.md)。期间原桥曾因一次认证拒绝停止；沿原单元恢复后仍观察到 10 秒 `CLIENT_OPEN` 超时。一次同预算的 legacy 握手诊断进入了业务轮，但 `LIST_EVENTS` 仍超时，故没有把诊断宣布为恢复，也没有据此放宽后台预算。最后原 collector 按既有网络退避自行恢复，2026-11-14 09:57:27 北京时间回读 `OK / ROUND_COMPLETE`。原缓存、正常后台模式与预算保持。
